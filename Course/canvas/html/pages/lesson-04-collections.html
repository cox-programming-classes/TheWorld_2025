Lesson 4 · Building a Game in C#

Collections

Many things, and what many costs.  A List holds things -- the rules are yours to write.

New idea: A collection is itself an object, with its own state and its own rules   |   Builds on: Lessons 1 through 3.  Your dice are fixed once built, they arrive valid, and their behavior lives beside them.  The container is the last thing left to design.

What you will be able to do

  • Write a type that wraps a collection and owns every rule about it
  • Say what IReadOnlyList<T> buys you -- and what it leaves open
  • Use { get; private set; } for state that changes, and defend it against both init and a public setter
  • Write the Fisher-Yates shuffle from the idea, in place, and seeded so a test can repeat it
  • Decide how a collection reports running out, and defend the choice you made
  • Read a foreach loop and the LINQ that replaces it, and pick between them on purpose

New words

collection -- an object whose job is holding other objects
List<T> -- the workhorse.  Ordered, resizable, and entirely without opinions about what goes in it
IReadOnlyList<T> -- a view of a list offering reading and counting.  A statement about what a caller may do with it
encapsulation -- keeping state private and making methods the way it changes.  Lesson 2 did this for construction; today does it for change
Fisher-Yates -- the shuffle.  Walk from the end, and swap each item with one chosen from the part you have yet to visit
LINQ -- .Where(), .Count(), .OrderBy().  Loops that come with names

Before you code

💭 Think about it

Run it before you change anything.  Six scenes, and every one of them is a List doing exactly what a List does, in a place that needed something with rules.  Then one question, and it has a real answer:  DiceBag.Add() checks the capacity and refuses politely.  Scene 2 puts nine dice in a bag of six anyway.  Who is at fault?

How it works

A List is indifferent, and that is correct of it

Ask what List<Dice> knows about dice bags.  The answer is the whole point:  it knows how to hold things, and that is the end of the list -- the same type carries shopping lists, pixels, and enemies.

Generality is the feature.  It is also exactly why the rules have to live somewhere else, and today you write the somewhere else.

A rule with a bypass is a suggestion. Add() did its job.  So did List.  The fault is that the rule was written in a place anybody could walk around.

Lesson 1, at a larger size

☕ If you're coming from Java

You have met this exact hole.  final List<Card> cards seals the field and leaves the list wide open, which is the same sentence with different keywords.

Collections.unmodifiableList() is the closest thing to IReadOnlyList<T>, and it carries the same caveat:  it wraps a view around a list somebody else may still be holding.

  • The difference worth naming:  C# hands you IReadOnlyList<T> as a return type you can declare, so the intent shows up in the method signature rather than at the call.

Scene 4 is the one to slow down on.  Contents is { get; init; }, so the slot is sealed.  One var snapshot = bag.Contents; later, a caller is holding the bag's insides and can empty it.

Making the reference fixed and making the thing it points at fixed are two separate decisions. Lesson 1 made the first.  Today makes the second.

This is why init was worth learning, and why today is the other half of it.

Who may change what

Three forms for a member, and every one of them is a claim you are making out loud:

  • { get; init; } -- set once, at construction, and settled.
  • { get; set; } -- anybody, any time, for any reason.
  • { get; private set; } -- this changes, and this type decides when.

Honest about empty

Draw from an empty bag and read the crash out loud:  Index was out of range. Those are List's words, about an index, and the word "index" belongs to List alone.  Lesson 2, arriving again.

So how should a bag report that it is out?  Throw, hand back null, or the Try pattern? All three are defensible and Lesson 2 gave you the framework to argue it.

Pick one.  Be ready to say what would change if your game had fifty decks running at once.

A loop, and then a name for it

☕ If you're coming from Java

.Count(d => ...) is stream().filter(...).count(), with the stream step left implicit.

LINQ is where extension methods from Lesson 3 get their biggest payoff:  every one of these is a static method on IEnumerable<T> that C# lets you call as though the list owned it.

Count the d20s in the bag with a foreach.  You have written that loop a hundred times in another language, so write it once more here.

Then meet .Count(d => d.Sides == 20) and read it against the loop you just wrote.  It is the same loop with a name on it.

That is the whole introduction.  LINQ is available from here on, and it stays optional -- pick whichever you would rather read in six months.

Build it step by step

  1. Read DiceBag.cs all the way through.  Two columns:  every rule the type is trying to enforce, and how a caller gets around it.
  2. Make the list private and hand out a read-only view.  private readonly List<Dice> _contents = []; and public IReadOnlyList<Dice> Contents => _contents;
  3. Re-run.  Scene 4 stops compiling, and that is the win -- CS1061, IReadOnlyList<Dice> does not contain a definition for Clear.  Scene 2 stops too.  Delete those lines, and say what deleting them proves.
  4. Fix Draw.  It should remove what it hands back, and be honest when the bag is empty.  How it is honest is your call -- and you defend it at the wrap-up.
  5. Fix Shuffle.  The algorithm inside it is already correct.  Find the bug in the signature before you touch the body.
  6. DrawnCount is a fact about what happened, so make it { get; private set; } and let the bag be the only thing that writes it down.
  7. Standard() built its bag with a collection initializer, which reached the list directly.  Rebuild it out of Add() calls.  The factory now goes through the same door as everybody else.
  8. Count the d20s with a foreach loop.  Then write it as .Count(d => d.Sides == sides) and decide which one you would rather read in six months.

Starter code

This code runs exactly as it is.  Get it running first, then start changing it.

The bag as it ships - every rule here is a suggestion
public class DiceBag
{
    public int Capacity { get; init; } = 6;

    // TODO (Step 2):  public, and a List.  Between those two facts,
    // every rule below is a suggestion.
    public List<Dice> Contents { get; init; } = [];

    // This method is careful.  It checks, and it refuses politely.
    // Scene 2 walks straight past it.
    public bool Add(Dice dice)
    {
        if (Contents.Count >= Capacity) return false;
        Contents.Add(dice);
        return true;
    }
}

Fisher-Yates, walking from the end
public void Shuffle()
{
    for (var i = _contents.Count - 1; i > 0; i--)
    {
        // The partner comes from the part we have yet to visit.
        // Picking from the whole list every time looks fine and is biased.
        var j = _random.Next(i + 1);
        (_contents[i], _contents[j]) = (_contents[j], _contents[i]);
    }
}

Make it yours

⭐ This is the part that matters most. Pick at least one and make it yours.

  • Deck. Fifty-two cards, shuffled, dealt one at a time, and honest about running out.  The same three problems you just fixed, on a type you designed yourself.
  • Hand. A collection with a limit.  Deal five cards into it and have it refuse the sixth.
  • Then the payoff, and it closes the whole unit: deal one five-card hand and score it with both rule sets from Lesson 3.  Same cards, two games, two answers -- with each rules file ignorant of the other.
  • Four lessons of separate ideas, running together in one line of output.  That is what the milestone is built on.

Finished early? Deal until the deck runs out, and make it end the way you argued it should in class.  Then hand your Deck to the person next to you and ask them to break it.  They will reach for the thing you left public.
