Data Validation and Factory Methods

Where does "is this legal?" live? One door in, one place the rules are written.

New idea: A type should be impossible to construct in an invalid state   |   Builds on: Lesson 1. Your dice are already immutable -- that is what makes today's move worth anything.

What you will be able to do

  • Write a guard clause that refuses a bad value where the mistake was made, and say what validating late costs instead
  • Make a constructor private and expose factory methods, so that every caller comes through the rules
  • Write factories that compose -- each one calling the general factory and leaving the rules where they are
  • Choose between throwing and returning false, based on where the bad value came from

New words

guard clause -- a check at the top of a method that refuses bad input and gets out immediately
invariant -- something that is true about an object for its entire life, because the type holds it that way
exception -- an error that travels up the call stack looking for somebody who knows what to do about it
factory method -- a static method that builds an object -- so construction can say what it is for, and can refuse
the Try pattern -- TryParse(input, out result) returning bool. C#'s way of saying "this might fail, and failure here is Tuesday"

Before you code

💭 Think about it

Last week you made dice that hold still. So how many moments are there, now, when a set of dice can be wrong? Count them. Then look at the museum in Scene 1 and decide which exhibit worries you most -- and be ready to argue about it, because the expensive one is probably the quiet one.

How it works

Immutability collapsed the problem

If a value can only ever be set while the object is being built, then the moment it is built is the only moment it can be wrong.

That is an enormous simplification and it came free with the decision you already made last lesson. Today we stand on that one moment and put a door on it.

Loud failure is cheap. Quiet wrongness is expensive.

Scene 1 builds eight sets of dice. Some are refused. Some roll happily. One is accepted and then detonates.

The instinct is to say the crash is the worst one. Look again. The crash told you immediately, at the line where you made the mistake. The 1d0 shipped.

Read the crash message when you get to it: 'minValue' cannot be greater than maxValue. Everybody in this room can see those are somebody else's words. That message came from inside Random. Your bad value walked out of your type, into somebody else's code, and blew up there -- in their vocabulary, pointing at their variable names.

That is what validating late buys you.

One door in

☕ If you're coming from Java

You may already know this one, and if so you are ahead of the lesson.

"Consider static factory methods instead of constructors" is the opening item of Effective Java, and the reasons Bloch gives are the reasons here: a factory has a name, it can refuse, and it is free to hand back an object that already exists.

So this is the same idea you have already met, and the language you know reached for it too.

  • What C# adds is Dice.D20 -- a shared instance handed out by a factory, which is only safe because Lesson 1 made it unchangeable. In Java you would be reaching for the same trick and worrying about the same thing.
  • The Java habit to actually drop is the parameterless constructor plus setters. A private constructor ends that shape, and rightly so.

Open Dice.cs and look at the constructor. It is private, and it trusts its three numbers completely. It can afford that, because this file is the only place that can reach it.

Try writing new Dice(0, 0) in Program.cs. The compiler rejects it.

  • Every one of them defers to Of(). Attack is one line. TryParse does string work and then hands off.
  • One door, one place the rules are written, and every caller through it.
  • A constructor gets one name and has to accept whatever it is given. A factory gets as many names as your game has ideas -- and gets to refuse.
The constructor, and the only things that can reach it
private Dice(int count, int sides, int modifier)
{
    Count = count; Sides = sides; Modifier = modifier;
}

// Everything that CAN call it is a factory method:
Dice.Of(2, 6, 3)          // the general front door - the rules live here
Dice.Attack(3)            // a named archetype        -> calls Of
Dice.AbilityScore()       // another                  -> calls Of
Dice.ByName("attack")     // a key from a save file   -> calls Attack -> Of
Dice.TryParse("2d6+3")    // text from outside        -> calls Of
Dice.D20                  // a shared preset          -> calls Of

Throw, or hand back false?

☕ If you're coming from Java

The split itself will be familiar -- it is roughly Java's checked versus unchecked exceptions, drawn along the same line: is this the caller's mistake, or a thing that just happens?

The mechanism differs. C# leaves every exception unchecked, so handling stays the caller's decision and the throws clause is absent entirely. What C# reaches for is the Try pattern: a bool return plus an out parameter.

  • If you know Optional<T>, this is the same job done with a different tool -- and a noisier one. out is genuinely awkward syntax; it is also everywhere in the standard library, so it is worth being fluent in.
Java:  int n = Integer.parseInt(s);   // throws
C#:    int.TryParse(s, out var n)     // returns false

Two different failures, two different answers. The question to ask is where did it come from.

  • Bad value from your own code → throw. Fail loudly, at the mistake.
  • Bad value from a file, a player, a mod, a network → TryParse. Return false and carry on.
  • Both go through the same guards. TryParse catches the refusal and turns it into an answer.
  • out var dice is a second thing the method hands back, alongside the bool.
Same rules, two paths
Dice.Of(0, 6)                              // I wrote this.  If it's wrong, that's a BUG.     -> throw
Dice.TryParse(whatThePlayerTyped, out var d)   // They wrote this.  If it's wrong, that's Tuesday. -> false

Normalize, or reject?

A value can be wrong in two different ways, and the line between them is yours to draw.

  • Formatting is noise. " 2d6 ", "2D6", "2d6" are one claim typed by three people. Clean it up quietly; everything meaningful survives. (TryParse already does this for you. Find the line.)
  • Meaning is a claim. "0d6" says something false. Refuse it.
  • Where does "2 d 6" go? You and the person next to you will disagree, and you each need a reason.

Two forms for the limits, and why

☕ If you're coming from Java

Your fingers are going to type public static const int exactly once, because Java spells this static final. C# will stop you with CS0504 -- the constant cannot be marked static -- because a const is already static and saying so twice is one word too many.

The second form stands on its own, with the closest Java equivalent some way off. public static int MaxCount => 100; is a property: it is recomputed every time it is read, which is why it needs the static keyword that a const carries on its own.

  • Java's naming convention would be MAX_COUNT. C#'s is MaxCount -- PascalCase for everything public, constants included.
Java:  public static final int MAX = 100;
C#:    public const  int Max = 100;    // already static
C#:    public static int Max => 100;    // a property

Look at the top of Dice.cs. MinSides is a const. The other three are static properties. That is a claim about how permanent each number is.

  • A const is already static. You reach it as Dice.MinSides, straight off the type. If you learned static final somewhere else, your fingers will try public static const exactly once -- that is CS0504.
  • public static int MaxCount => 100; is a property. It is computed each time it is asked for, which is why it needs the static keyword that a const carries on its own.
  • Only a const can appear in a pattern. The guards could have been written as count is >= 1 and <= MaxCount, which is idiomatic modern C#. A pattern requires a const, and MaxCount is a property. Try it and read CS9135.
  • Go break that last one on purpose. Knowing which compiler errors are real design rules and which are just syntax is worth five minutes.
The form is the documentation
public const  int MinSides    = 2;      // STRUCTURAL - a die with fewer than two faces
                                        // to choose between, in this game or any other

public static int MaxCount    => 100;   // HOUSE RULES - this table's numbers.  Another
public static int MaxSides    => 1000;  // game picks different ones and is still
public static int MaxModifier => 20;    // playing with dice

Starter code

This code runs exactly as it is. Get it running first, then start changing it.

The worked example - the count guard, already written
public static Dice Of(int count = 1, int sides = 6, int modifier = 0)
{
    // A guard clause:  check it, complain immediately, get out.  The alternative is
    // to accept it, carry on, and fail somewhere else an hour later, with the
    // origin of the bad value long since lost.
    if (count < 1 || count > MaxCount)
        throw new ArgumentOutOfRangeException(
            nameof(count), count, $"A roll uses between 1 and {MaxCount} dice.");

    // TODO (Step 4): sides is wide open.
    // TODO (Step 5): modifier is wide open too.

    return new Dice(count, sides, modifier);
}
The Try pattern - one copy of every rule
public static bool TryParse(string? notation, out Dice dice)
{
    dice = D6;
    if (string.IsNullOrWhiteSpace(notation)) return false;

    // Formatting is noise:  clean it up quietly, before anything else looks at it.
    var text = notation.Trim().ToLowerInvariant();

    // ... string work:  split on 'd', pull out a count and a modifier ...

    // Of() is still the only way to make dice, so every rule you wrote up there
    // applies to text from outside too.  Every rule stays where it is.
    try
    {
        dice = Of(count, sides);
        return true;
    }
    catch (ArgumentOutOfRangeException)
    {
        return false;
    }
}

Make it yours

⭐ This is the part that matters most. Pick at least one and make it yours.

  • Open your Card.cs from Lesson 1 and do to it what we did to Dice.
  • Break it on purpose first. Before writing a single guard, construct the five worst Cards your design allows. A card missing its suit. A rank of 47. A rank of -3. Print them. Sit with it.
  • Sort each failure into noise (fix it quietly -- "ace of spades", "ACE OF SPADES", " AS ") or a claim (refuse it -- rank 47). Say where you put the line.
  • Make the constructor private. Then work out what factory methods your game actually wants. Card.Of(rank, suit)? Card.AceOf(suit)?
  • Give Card a TryParse. "AS" is the ace of spades, "10H" the ten of hearts. Then survive these: "2c", " KS ", "1S", "11H", "ZZ", "", "10".
  • Write a factory that hands back a full standard deck. Fifty-two cards, each one distinct, the whole grid covered. Prove it -- print the count.

Finished early? Count how many of your own factory methods restate a rule in place of calling through to one place. Every one that does is somewhere your future self can forget to update. Fix them, then say how many you found.
