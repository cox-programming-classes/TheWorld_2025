Extensions and Separating Concerns

Some of what a thing can do belongs somewhere else.  Change code that works, and say what you bought.

New idea: Behavior can live beside the data it describes   |   Builds on: Lessons 1 and 2.  Your dice hold still and arrive valid -- which is precisely what makes today safe.

What you will be able to do

  • Write an extension method -- and an extension property, instance or static
  • Decide whether a behavior belongs on a type or beside it, using a test you can apply to code you are seeing for the first time
  • Apply that same test to a constant, and notice that a number can encode policy just as much as a method can
  • Use namespaces and using deliberately -- as a statement about what a file is allowed to depend on
  • Explain what extension methods do in place of polymorphism, and predict the two places that bites

New words

extension method -- a static method C# lets you call as though it were an instance method on another type
extension member -- the general form.  C# 14's extension(Dice) / extension(Dice dice) blocks add properties too, static or instance
separation of concerns -- keeping "what a thing is," "how it is shown," and "what it means here" in different places
coupling -- what a piece of code has to know about in order to work
refactoring -- changing structure while behavior stays identical.  The output is the proof
compile-time binding -- the compiler picks which method runs using the type the variable is declared as, leaving what it holds at runtime out of it

How it works

The three lessons are one argument

It is worth saying the whole shape out loud now, because today is where it pays off:

  • Lesson 2 -- therefore there is exactly one moment it could be wrong, so close it.

A type that knows what a screen is

Dice.cs uses Console.ForegroundColor.  Ask what that type now requires in order to exist:  a terminal, a screen, a human looking at it.

And we want to unit-test this.  And put it on a web page.  And run it on a server where the console is absent entirely.

A type that knows what a screen is can only ever live where screens are.

The three ingredients

☕ If you're coming from Java

Java leaves this one to C#. This is the biggest single gap between the two languages in this whole course.

When Java wants behavior that belongs beside a type, it writes a static utility class and you call it inside-out:  Collections.sort(list), Objects.equals(a, b), Arrays.asList(...).  The helper's name comes first and the thing you care about is an argument.

C# lets that exact same static method be called as though it were on the type.  Same method, same compiled call -- it just reads in the order you think in.

  • This is why LINQ can exist.  list.Where(...).OrderBy(...) is a chain of extension methods on IEnumerable<T>, and Java's answer -- streams -- needed a .stream() call and interface changes to get something similar.
Java:  DiceDisplay.describe(dice)
C#:    dice.Describe()
       // identical after compiling

An extension method is exactly three things.  Once they are true, dice.Describe() compiles as though Describe had always been part of Dice.  Dice.cs has yet to hear of it.

All of it
public static class DiceDisplay                  // 1. static class
{
    public static string Describe(this Dice dice) // 2. static method
    {                                             // 3. `this` on parameter one
        ...
    }
}

So why bother, if the call site is identical?

The call site stays put either way, so the value lies elsewhere.  It is:

  • Dice.cs stops needing Console.  It stops knowing about colors, terminal widths, and box-drawing characters -- so it can be tested, served, embedded.
  • Everything about how dice look lands in one file, so the next person who wants to change that has one place to go.
  • Your game's rules stop being smuggled inside a type that claims to be about dice in general.
  • And the cost, which is real:  you now have to know Describe lives in a file you may have closed.  Namespaces are how you make that findable.  It is a trade, and that is what you pay.

The test for where something belongs

This is the transferable part -- the thing that outlives the syntax.  Imagine two games using this exact Dice type:  your dungeon crawler, and somebody's board game about trains.

  • The trains game needs it to behave identically → it is part of what dice are.  Leave it.
  • The trains game would want it to mean something else, or drop it entirely → it is a rule of your game.  Move it.
  • Apply that to IsCritical, IsFumble, Beats, and ChanceOfBeating.  They give different answers, and at least one is genuinely arguable.

Extensions cover more than methods

C# 14 lets you add members of any kind -- properties included -- to a type somebody else owns.  Two flavours, and you will want both today.

  • Same three ingredients:  a static class, a static member, a receiver declared up front.
  • Same rule too -- a real member on the type always beats an extension member with the same name.
  • The consequence worth sitting with:  once MaxCount is an extension property, Dice.MaxCount reads exactly as it did when it was a real member.  Every call site in the program reads them the same way.
Static and instance extension members
extension(Dice)                              // bare type name -> STATIC members
{                                            // these hang off the TYPE
    public static int MaxCount => 100;       //   Dice.MaxCount
}

extension(Dice dice)                         // with a name -> INSTANCE members
{                                            // these hang off a VALUE
    public bool IsLegalHere =>               //   myDice.IsLegalHere
        dice.Count <= Dice.MaxCount;
}

Two surprises, one fact

☕ If you're coming from Java

Both surprises come from the same place, and Java makes it easy to predict if you think about it the right way.

Java's static methods bind the same way -- they resolve on the declared type, leaving the runtime one out of it.  Extension methods are static methods wearing a friendlier syntax, so they inherit that limitation exactly.

The null one follows too:  DiceDisplay.summarize(null) is a perfectly ordinary call in Java.  The reference stays untouched, so the call comes back clean.  C# just lets you write it as missing.Summarize(), which is why it looks impossible.

  • The habit to keep:  when a C# method call surprises you, ask whether it is really an instance method.  If it is an extension, you are looking at a static call and the rules you already know apply.

Scene 4. There are two methods named Describe in scope -- an instance method on Dice, and an extension in DiceDisplay.  Only one ran, and it won cleanly.  The extension has been sitting there being ignored since you opened the project.

Scene 5. missing.Summarize() is called on null and comes back clean.

Both are the same fact:  dice.Summarize() is a static call in disguise.  The compiler rewrote it into DiceDisplay.Summarize(dice) before the program ever ran, using the type the variable is declared as.

  • So an extension method binds at compile time and stays fixed there, with virtual out of its reach.
  • What you are buying is readability.  That is worth a lot.  Spend it on that alone.

  2. The rule for the whole lesson:  Program.cs stays exactly as it is. If a move requires editing a call site, you moved something wrong.
  3. Move PrintHistogram into Display/DiceDisplay.cs.  Copy the body, make the first parameter this Dice dice, change bare Roll(rng) to dice.Roll(rng), and delete it from Dice.cs.
  4. Re-run.  Output byte-for-byte identical, Program.cs untouched. That is what refactoring means -- the behavior is the control group.  Output that changed means you edited.
  5. Sort IsCritical, IsFumble, Beats, and ChanceOfBeating using the trains test.  Argue the contested one, place it, and write one sentence in the file saying why.  Then move PrintRoll -- it depends on two of them, so it moves last.
  6. Move ToBoxArt.  Dice.cs should now be about half its old size.  Re-read what is left -- does it match your Step 1 list?
  7. Scene 4 calls dice.Describe().  Work out which of the two Describe methods ran, predict what the line prints once you delete the other, then delete Dice.Describe() and check.  An instance method always wins, and it wins silently.
  8. Add one presentation the file has yet to carry -- ToShortString(), a table of dice in columns, ToOdds(int dc).  It should leave Dice.cs untouched.
  9. Round two:  the numbers. Run the trains test on the four limits at the top of Dice.cs.  Three of them fail it.  Move those three into an extension(Dice) block in DiceRules -- the lines copy across unchanged -- and delete them from Dice.cs.
  10. Two things happen and both are the lesson.  IsLegalHere keeps working untouched, because it reads the member the same way either side of the move.  And Dice.Of() stops compiling -- resist fixing that with a using, which would make the dice depend on one game's rulebook.  Fix it by asking what those guards were doing in Of() in the first place.  One of the three disappears entirely; work out which and say why that is the right outcome.
  11. Delete a using from Program.cs.  Read what breaks.  Put it back.  Did anything break that caught you by surprise?  Those are the good ones.

Starter code

This code runs exactly as it is.  Get it running first, then start changing it.

The worked example, already moved for you
namespace Toolkit.Display;

public static class DiceDisplay
{
    /// <summary>One line a player could read.</summary>
    public static string Describe(this Dice dice)
    {
        var spread = dice.Minimum == dice.Maximum
            ? $"always {dice.Minimum}"
            : $"{dice.Minimum} to {dice.Maximum}, averaging {dice.Average:0.#}";
        return $"{dice} ({spread})";
    }

    /// <summary>Note the `?`.  This one survives being handed an empty variable.</summary>
    public static string Summarize(this Dice? dice) =>
        dice is null ? "(the slot is empty)" : $"{dice}, {dice.Minimum}-{dice.Maximum}";
}
Where the numbers end up in Step 9
public static class DiceRules
{
    extension(Dice)
    {
        public static int MaxCount    => 100;    // moved from Dice.cs, unchanged
        public static int MaxSides    => 1000;
        public static int MaxModifier => 20;
    }

    extension(Dice dice)
    {
        // Untouched since Step 1.  It still says Dice.MaxCount, and it reads
        // a real member and an extension member the same way.
        public bool IsLegalHere =>
            dice.Count <= Dice.MaxCount
            && dice.Sides <= Dice.MaxSides
            && Math.Abs(dice.Modifier) <= Dice.MaxModifier;
    }
}

Make it yours

⭐ This is the part that matters most. Pick at least one and make it yours.

  • Split your Card.cs into three: Toolkit.Cards (what it is), Toolkit.Cards.Display (what it looks like), Toolkit.Cards.Rules (what it is worth).
  • Display is mechanical:  a short form (A♠), a long form (Ace of Spades), a drawn card.
  • The rules half is where this gets real, because a card's value belongs to the game being played. In blackjack an ace is 1 or 11 and a king is 10.  In war a king beats a jack and an ace beats everything.  In hearts the queen of spades is worth thirteen points of misery.
  • One Card type.  Three games.  If card.Value is a property on Card, which of those three did you just pick a side in -- and where does that leave the other two?
  • Write the rules for two of those games as separate extension classes.  Then look at the two files sitting side by side and say what that arrangement bought you.
  • Prove the separation is real: delete a using and show that exactly the code you expected stopped compiling.
