First Objects

Complexity, and managing mutability. Find the bug hiding inside working code.

New idea: Immutability is declared member by member -- and record governs something else   |   Builds on: Any language you already know. It does assume you have written objects somewhere before.

What you will be able to do

  • Build a complex type out of primitives, and defend each primitive you picked
  • Predict when assigning one variable to another makes a copy and when it makes a second name for the same thing
  • Turn a mutable type into an immutable one, and repair every call site the compiler flags
  • Say what immutability actually bought you, which goes well past "the bug went away"

New words

value type -- the variable holds the thing itself. int, double, bool, char. Copying the variable copies the thing
reference type -- the variable holds where the thing is. Every class and every record. Copying the variable copies the address
immutable -- fixed once it exists. string already is. Dice will be by the end of today
record -- a type C# compares by the values it holds
init-only -- settable while the object is being built, and sealed from then on. Spelled { get; init; }
aliasing -- two names for one object. Fine, right up until the day it bites

Before you code

💭 Think about it

You have shipped this bug before, in another language. Somewhere, you changed a thing in one place and watched it change somewhere across the room. What language were you in, and what was the thing -- a list, a dictionary, an object? And whose job was it to stop that from happening?

How it works

The object you already know how to write

You have built Dice before. Some fields, a getter and a setter on each, methods underneath. That shape gets taught first almost everywhere: an object is a box of state, and methods are how you reach in and change it.

This course leans the other way, because modern C# does:

  • an object has state you change  →  a value is its data, and holds still
  • setSides(4) -- reach in and modify  →  build a different one and use that
  • two objects are equal if they are the same object  →  two values are equal if they say the same thing
  • behavior lives on the object  →  behavior can live beside the data (that is Lesson 3)

Both columns are defensible

They are different bets about what goes wrong in a large program, and each one buys something the other gives up.

The right-hand column is the one you have yet to meet, and it is where C# has been heading for ten years. Both are defensible.

What record governs, and what it leaves to you

☕ If you're coming from Java

This one is a real departure, and it is easy to miss because the syntax looks familiar.

In Java, == on two objects asks are these the same object in memory -- and it says false for two identical-looking things. To compare contents you override equals() (and then hashCode(), and then you keep them in sync forever).

A C# record writes both of those for you, and wires == to use them. Two separately-built 2d6+3s are equal because they say the same thing.

  • This is a property of record. A plain C# class behaves exactly like Java, where == compares identity and Equals is yours to override.
  • So record vs class is a real decision about what your type means, well past a matter of style.
Java:  a.equals(b)   // you write equals()
C#:    a == b        // the record wrote it

Dice is already a record on the first line of the starter. That gets you value equality for free:

  • Immutability stays a separate decision, made per member.
  • Scene 2 is a record misbehaving exactly the way any mutable object would.
  • The protection lives one keyword away, and you are about to write it.
What a record hands you
var a = new Dice { Count = 2, Sides = 6, Modifier = 3 };
var b = new Dice { Count = 2, Sides = 6, Modifier = 3 };

a == b        // True - two objects, same three numbers, a record calls that equal

What a variable actually holds

☕ If you're coming from Java

This part is familiar territory, and that is worth saying out loud.

Java works exactly this way. Primitives copy their value; objects copy a reference. String is immutable there too, for the same reason and with the same consequences.

So Scene 2's bug is one you could have written in Java this morning, with Java looking on just as calmly. That is the point of the lesson.

This is why Scene 2 happens, and it is the whole mechanism:

  • A string is a reference type that behaves like a value, because it is fixed at creation.
  • ToUpper() leaves the original alone and builds a second string to hand back.
  • That third picture is the target. By the end of today, Dice behaves the way string already does.
Three pictures
int a = 5;
int b = a;              // a VALUE - copying copies the number itself
b = 9;                  // a is still 5.  Two boxes, two numbers.

var first  = new Dice { Sides = 20 };
var second = first;     // a REFERENCE - copying copies the address
second.Sides = 4;       // first.Sides is now 4 too.  Two boxes, ONE die.

string name = "goblin";
string loud = name.ToUpper();   // name is unchanged - a string is fixed at birth

The one keyword

☕ If you're coming from Java

You have done this before, with final fields set in the constructor. Same intent, and it works.

The difference is cost. In Java that means a field, a constructor parameter, a getter, and a setter left off -- four things to keep straight. In C# it is one keyword on one line, which means you will actually bother to do it on the members that deserve it.

  • Java's final also stops at the reference, exactly like init does. A final List can still have things added to it.
  • Java's record sits elsewhere. It is much closer to C#'s positional records -- genuinely immutable and terse. C#'s record keyword is the looser of the two, which is why Dice can misbehave in Scene 2 at all.

Every member you write is a decision about who may change it and when. C# makes you say which one you mean.

  • Every option here is a choice. { get; set; } is the one you make by staying quiet.
  • There is a third, private set, for things that genuinely should change. It waits for Lesson 4.
The two dials that matter today
public int Sides { get; set;  }   // set any time, by anybody, from anywhere
public int Sides { get; init; }   // set while the object is being built, then sealed

Picking a primitive

Dice is three ints. That was a decision, and here is some of what it cost and bought.

  • int -- whole numbers. Counting anything: dice, gold, hit points.
  • double -- fast decimals, approximate. Measurements, averages, physics.
  • decimal -- slow decimals, exact. Money, or anywhere 0.1 + 0.2 has to equal 0.3.
  • That second line is the dangerous one. 7 / 2 giving 3 runs clean, stays quiet, and sails through every test.
  • A die comes in whole numbers, so int is right here. It is right sometimes, and "the default" is a poor reason to pick anything.
Run these and read them carefully
7 / 2                 // 3      - both sides are int, so the answer is int
7 / 2.0               // 3.5
0.1 + 0.2 == 0.3      // False  - double is fast and APPROXIMATE
0.1m + 0.2m == 0.3m   // True   - decimal is exact and slow

Starter code

This code runs exactly as it is. Get it running first, then start changing it.

Dice.cs - as it ships
public record Dice
{
    public int Count { get; set; } = 1;
    public int Sides { get; set; } = 6;
    public int Modifier { get; set; } = 0;

    public int Roll(Random rng)
    {
        var sum = Modifier;
        for (var i = 0; i < Count; i++)
            sum += rng.Next(1, Sides + 1);   // Next(1, 7) gives 1..6 - the top is exclusive
        return sum;
    }

    public int Minimum => Count + Modifier;
    public int Maximum => Count * Sides + Modifier;
}
Scene 2 - the cursed d20
var partyDie = new Dice { Count = 1, Sides = 20 };
Console.WriteLine($"The die on the table:  {partyDie}");   // 1d20

// Your character has a +5 attack bonus, so you pick up the die and...
var yourDie = partyDie;
yourDie.Modifier = 5;

Console.WriteLine($"Your die:              {yourDie}");     // 1d20+5
Console.WriteLine($"The die on the table:  {partyDie}");   // 1d20+5   <-- ???

// The goblin is now attacking you with your own +5 bonus.
// Every line here did exactly what it says.

Make it yours

⭐ This is the part that matters most. Pick at least one and make it yours.

  • Start your own Card.cs. A file you create yourself, in the same folder. It follows you to Lesson 2 and Lesson 3, and it is the one file in this course that is unambiguously yours.
  • Build a Card -- the card alone, with the game left for later. Then answer, in the design of the type itself: what about a card is fixed for good, and what about it can change?
  • Rank and suit. Does the Ace of Spades ever become something else? What does your answer mean for how you declare them?
  • Face up or face down. Is that a fact about the card, or about where the card currently is? Those have different answers, and the second one may belong to the table.
  • How do you say "Queen"? A string "Q"? A number 12? C# has a type built for "one of a fixed set of named options." Go find out what it is called.
  • Should two separately-created Aces of Spades be equal? Try it before you decide. C# has an opinion and it depends on what you declared.

Finished early? Make one member of your Card that you are genuinely torn about, write both versions, and keep the one you can defend better. Bring the one you threw away -- that is the more interesting half of the conversation.
