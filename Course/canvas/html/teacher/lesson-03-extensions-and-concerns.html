Lesson 3

Extensions and Separating Concerns

Some of what a thing can do belongs somewhere else.  Change code that works, and say what you bought.

TimingTwo meetings (~50 min each)
New ideaBehavior can live beside the data it describes
Builds onLessons 1 and 2.  Your dice are fixed once built and arrive valid -- which is precisely what makes today safe.
StandardMove behavior off a type using extension members, decide what belongs where using a stated test, and prove the refactor changed structure while behavior stayed the same.

Warm-up (~8 min)

Read Dice.cs all the way through before you touch anything.  It is about 220 lines.  Then answer one question:  how many different jobs is this type doing? Write the list down -- you will check against it at the end.  And note that every method in that file was a reasonable idea on the day it was written.

Direct instruction (~12 min)

Hold off on running anything

Open Dice.cs on the projector and scroll through it slowly, top to bottom, in silence.  Then:  "How many different jobs is this type doing?"

Take the list on the board.  They will get to roughly:  what dice ARE (Count, Sides, Modifier, the guards) / how dice ROLL / how dice are MADE / how dice LOOK / what dice MEAN here.

Then two questions that set up everything.  First:  "Which of these did somebody do wrong?" Every one of them was a reasonable idea on the day it was written.  Say that explicitly -- if they think this is a lesson about bad code they will learn the wrong lesson, namely be clever up front.

Second:  "Dice.cs uses Console.ForegroundColor.  What does this type now require in order to exist?" A terminal.  A screen.  A human.  Then:  "We want to unit-test this.  And put it on a web page.  And run it on a server where the console is absent entirely."

Leave this on the board all lesson:  A type that knows what a screen is can only ever live where screens are.

Now run it.  Everything works, beautifully.  That is the point.

The three ingredients, and the honest cost

Open Display/DiceDisplay.cs and point at exactly three things:  static class, static method, this on parameter one.  That is the whole mechanism.

Then ask where the value is, since the call site stays put.  Steer to:  testable/serveable/embeddable, one place to change how dice look, rules stop hiding inside a general type.

Then the cost, in your words, before they find it themselves:  "You now have to know Describe lives in a file you may have closed.  That is real.  Namespaces make it findable.  It is a trade, and here is what you pay."

The trains test

The transferable part.  "Two games use this exact Dice type -- your dungeon crawler, and somebody's board game about trains.  Does the trains game need this to behave identically?  Then it is part of what dice ARE. Would the trains game want it different, or drop it entirely?  Then it is a rule of YOUR game."

Apply it live to the four candidates.  IsCritical and Beats go fast.  ChanceOfBeating is the argument -- pure math about the dice, phrased entirely in one game's difficulty vocabulary.  Let them fight.  Both placements are defensible; saying why is the assessment.

If Lesson 2 left "is 1d20-50 valid?" hanging -- and it should have -- this is where it lands.  That check belongs in Rules.  It always did.  There was nowhere to put it.

The two surprises

Have them PREDICT both before running.  Scene 4: two Describe methods in scope, the instance one wins, the extension has been sitting there ignored since they opened the project.  Scene 5: missing.Summarize() on null comes back clean.

Same fact twice:  dice.Summarize() is a static call in disguise.  The compiler rewrote it to DiceDisplay.Summarize(dice) before the program ran, using the DECLARED type.

"So an extension binds at compile time and stays fixed there, with virtual out of its reach.  What you are buying is readability.  That is worth a lot.  Spend it on that alone."

Leave virtual alone.  Name it as Lesson 5's business and leave the hook.

Round two -- the numbers (save this for Meeting B)

Save this for Meeting B, on its own.  Open with it.

Show the extension block syntax and name the two flavours:  extension(Dice) for static members, extension(Dice dice) for instance members.  Then point at the four limits and ask the trains test one more time.

The moment worth engineering: have them predict what breaks when MaxCount leaves Dice.  They will say IsLegalHere, because it says Dice.MaxCount.  It keeps working, because it reads them the same way.  What breaks is Dice.Of(), which is the one place they expect to stay safe, and it breaks because Of() was quietly enforcing a house rule that belonged to the table.

Then let them find that modifier's guard has nowhere to go at all.  That guard was 100% policy.  It leaves, and Dice is more correct for losing it.

Expect pushback:  "so anyone can make 1d20-500 now?" Yes.  And it is a perfectly good die that this table refuses.  The type's job is to guarantee a die, and the rulebook belongs elsewhere.  Sit in that discomfort with them for a minute and leave it there -- it is the same discomfort that makes people put every rule in the constructor in the first place.

Guided activity (~22 min)

  1. Step 3 on the projector WITH them, out loud, before they read it.  The moment to hit:  run before, run after, point out that Program.cs is untouched and the output is identical.
  2. Name the technique explicitly:  "Behavior is the control.  Output that changed means you edited." For most students this is the first refactor they have run with a control group -- they change structure and behavior at once, something breaks, and the cause is anyone's guess.  They will use this for the rest of their lives.
  3. Step 5 individually, but take the ChanceOfBeating argument as a whole class.  Two minutes, left open.
  4. Step 7 (deleting Dice.Describe()) as a class -- have them predict the new output before deleting.
  5. Steps 9 and 10 are Meeting B and are the payoff.  Protect the time; do the prediction moment together.
  6. Release to Cards for the back half of Meeting B. The blackjack/war split is the centre of it.

Common mistakes to watch for

  • Moving PrintRoll before deciding where IsCritical lives, hitting a compile error, and moving IsCritical into Display to make it stop.  Very common, entirely logical, exactly wrong.  Ask:  "so a natural 20 is a display concern now?"
  • Losing the this keyword, producing a confusing error.  One-line fix, but let them read the error first.
  • Making EVERYTHING an extension, including Roll. Ask what happens when they want a WeightedDice that rolls differently.  Leave it hanging -- that is Lesson 5, and this is the best possible way for the question to arrive.
  • Fixing the Step 10 break by adding using Toolkit.Rules; to Dice.cs. It compiles.  It is also backwards, and it is worth stopping the room over:  the dice would now depend on one game's rulebook.
  • Over-application. Some students will come out of this wanting six files per type.  Say the quiet part:  "Three similar lines beat a premature helper.  Split when the mixing has cost you something you can name." Dice.cs earned its split by growing for four fictional weeks.  A forty-line type has earned the right to stay one file.

Wrap-up (~5 min)

Ask: Name one thing you left on Dice, and one thing you moved off it.  For each, say who would disagree with you and what they would have wanted instead.

Looking for: Anything specific with a named opponent.  The second half of the question is the assessment.  Also listen for whether they can state the COST -- three files where one used to do, and having to know Describe lives somewhere out of sight.  A student who thinks every refactor is a free win will refactor everything, forever.

Teaching notes

  • Pacing. Meeting A: 8 warm-up / 12 instruction / 22 guided (steps 1-7) / 5 wrap.  Meeting B: 5 recap on the trains test / 15 guided (steps 8-11) / 25 Cards / 5 wrap.
  • The Cards argument is the real assessment of this lesson. The strongest students go somewhere genuinely interesting:  an ace is 1 OR 11 depending on the rest of the hand, which makes blackjack's value a function of the HAND -- it is a function of the HAND. That is a real insight about where a rule lives and it should be praised loudly.  It is also Lesson 4 arriving early.
  • Weaker responses put Value on Card with a comment saying "blackjack rules." Fine for today.  Ask one question -- "what does the war game do now?" -- and move on.  They will hit it again when hands become real.
  • Forward hooks planted today. "Extensions resolve at compile time" → Lesson 5, virtual and WeightedDice. "Value depends on the hand" → Lesson 4, collections.  And "where does 1d20-50 get rejected?" → answered today, finally.
  • If they finish early: GameData/GameMechanics/ versus Engine/States/ in the finished game.  Same split, thirty files, and every console call in the domain model still goes through IGameIO -- that interface is the seam.  Ask them to find the one place a game state actually writes output.
  • Extension properties are C# 14 / .NET 10.  If a student's editor flags extension(Dice) as invalid syntax, check the SDK version before debugging anything else.

Rubric reference (no points)

Standard
Move behavior off a type using extension members, decide what belongs where using a stated test, and prove the refactor changed structure while behavior stayed the same.
Getting StartedEverything is still in one file, or the build went red after a move.  Next step: the most common miss is forgetting this on the first parameter -- leave it off and you have written a plain static method, so dice.PrintHistogram() stays unresolved.  The second most common is moving PrintRoll before deciding where IsCritical goes; move the things it depends on first.
Got It WorkingDisplay is in DiceDisplay, the game's rules are in DiceRules, Dice.cs has been cleared of Console, and Program.cs is untouched with identical output.
Made It Mine ⭐…and I split my own Card three ways and wrote two different games' rules as separate extension classes -- and I can name one thing I left on Card and one I moved off, and say who would disagree.
Went Beyond…and I went somewhere the lesson left open -- a third rule set that dropped in with Card.cs untouched, a genuine argument about ChanceOfBeating I can make from both sides, an extension property of my own, or the realization that blackjack's ace is a function of the hand.

⭐ Made It Mine is the goal for everyone. “Went Beyond” keeps its list open -- the examples are only starting points. Going somewhere the lesson left open is the whole idea.
