Lesson 2

Data Validation and Factory Methods

Where does "is this legal?" live?  One door in, one place the rules are written.

TimingTwo meetings (~50 min each)
New ideaA type should be impossible to construct in an invalid state
Builds onLesson 1.  Your dice are already immutable -- that is what makes today's move worth anything.
StandardMake a type impossible to construct in an invalid state, using a private constructor and composing factory methods, and choose correctly between throwing and the Try pattern.

Warm-up (~7 min)

Last week you made dice that hold still.  So how many moments are there, now, when a set of dice can be wrong?  Count them.  Then look at the museum in Scene 1 and decide which exhibit worries you most -- and be ready to argue about it, because the expensive one is probably the quiet one.

Direct instruction (~13 min)

Immutability collapsed the problem

Open with the callback, because it makes the whole style cohere:  "Last week you made dice that hold still.  So how many moments are there, now, when a set of dice can be wrong?"

One.  The moment it is built.  That is an enormous simplification and it came free with the decision they already made.  Today we put a door on that moment.

This is also the honest reason the private constructor is worth its ceremony.  Lesson 1 is what gives it teeth, since a locked constructor means something only when everything after construction is sealed too.

Fail where the mistake is

Show the count guard inside Of() -- already written.  Name it.  Point at the three parts of the exception:  which parameter, what value, what the rule is.

Contrast with the Random message they just read in Scene 1:  "An error message is written for the person who has to fix it.  Write it for them."

One door -- the move of the lesson

Have them try var d = new Dice(0, 0); in Program.cs.  The compiler rejects it.

"So how did Scene 1 make dice at all?" Put the list of factories on the board and ask what they have in common.  Then the payoff, which you want THEM to say:  "How many places do you have to write the rule that dice need at least one die?"

One.  The private constructor is what makes that guarantee real, because the compiler enforces it.  Politeness and convention would leave it optional.  It is the compiler refusing to let anybody route around Of().

Contrast explicitly:  a constructor gets ONE name and must accept what it is given; a factory gets as many names as the game has ideas, and can refuse.

Throw, or hand back false?

Show TryParse in the source ending with a try/catch around Of().  Same rules, both paths, one copy.  That is the thing to point at.

The out parameter is new to most of them.  One sentence:  "a second thing the method hands back, alongside the bool." Stop there.

Why the longhand constructor here? -- have the answer ready

Somebody will ask where the terse positional form went.  Two reasons, and the second is the one that matters.

Mechanically:  a primary constructor is always public in C#, and record Dice private(...) is a parse error, CS1514.  You choose a primary constructor or a private constructor.

Really:  a primary constructor is a PUBLIC front door with open space where a rule would go.  That suits a type whose data stands on its own perfectly well.  A save-file record, a parsed config line, a message shape.  Those are DTOs, and gating one behind a factory would be ceremony guarding an empty room.

The split they should end up with:  has invariants to protect → private ctor + factory.  Is a shape, data alone → primary constructor.  Primary constructors arrive with DTOs, post-fork, wherever save/load lands.  Hold them back here.

Guided activity (~22 min)

  1. Everyone runs the starter first.  Scene 1 is the hook and it needs to land before any instruction.
  2. Have the whole room try new Dice(0, 0) and fail to compile.  Ten seconds, and it makes the private constructor something they felt.
  3. Steps 4 and 5 individually.  Circulate -- the most common miss is writing the guard as a pattern and hitting CS9135.
  4. Step 6 is the longest and it is Meeting B. Have them run Scene 2 after each sub-step, one change at a time.
  5. Step 8, the counting exercise, as a whole class.  Protect it -- see notes.
  6. Release to Cards for the back half of Meeting B. The deck factory is what most will need help SCOPING; the writing comes easily.

Common mistakes to watch for

  • Guards written as patterns -- sides is >= MinSides and <= MaxSides -- producing CS9135.  This is a good error to hit.  The limits are properties, and a pattern requires a const to appear in a pattern.  Let them read it before you explain it.
  • New archetypes written as new Dice(...), which the compiler now rejects.  The error IS the lesson; point at it.  They must go through Of().
  • Archetypes that re-check a limit "just to be safe." Ask what happens when the limit changes.  Two copies of a rule is one copy plus a future bug.
  • TryParse handling the modifier BEFORE the split, so "1d4-1" splits on 'd' into "1" and "4-1".  Have them print text at each stage.
  • IndexOf('-') where LastIndexOfAny belongs -- works until something has a negative count.  Let it break; the error teaches it faster than you can.
  • try/catch everywhere, because an exception feels like a crash they should prevent.  Push back once, clearly:  catching an exception you are powerless to fix is worse than letting it through -- it hides the report and leaves the bug where it was.
  • Deck factory built with nested loops over hard-coded string arrays.  Works fine.  Ask what happens when a rank gets misspelled, and let that push them toward enums if they have yet to go there.

Wrap-up (~5 min)

Ask: Name one rule you wrote.  Is it protecting you from a bug in your code, or from bad data outside it?  Show me where it lives because of that.

Looking for: Any specific rule, correctly sorted.  The distinction to listen for:  a rule catching a programmer error should throw and live in Of(); a rule catching bad external data should be the TryParse path that catches that throw.  A student who says "both, it's the same rule" has actually got it -- there IS only one copy, and the two paths differ only in what they do with the refusal.

Teaching notes

  • Pacing. Meeting A: 7 warm-up / 13 instruction / 22 guided (steps 1-5) / 5 wrap.  Meeting B: 5 recap / 15 guided (steps 6-8) / 25 Cards / 5 wrap.
  • The thing to protect is step 8, the counting exercise.  Two rules, eleven call sites, zero duplication.  Skip it and "make the constructor private" reads as ceremony somebody imposed on them.  With it, it reads as the thing that made the counting come out that way.
  • Two arguments to leave open. First:  is "2 d 6" the same claim as "2d6"?  Genuinely arguable -- whitespace inside a token stands on different footing from whitespace around it.  Second:  is 1d20-50 valid?  The honest answer is that it is perfectly good dice notation and a terrible game rule, so the check belongs somewhere that knows about the game -- a layer still to come.  That layer is Lesson 3, and Lesson 3 is built to land exactly there.
  • If a student gets to "that belongs to the game, and the dice type is the wrong place for it," write their name down.  That is the whole arc of the next lesson arriving a week early, from a student, which is worth more than anything you can say.
  • The same shape appears in Cards immediately:  is a rank of 11 invalid, or is it a Jack?  Depends on the game.  Let them find it.
  • A hole you should know about and leave alone. A record still supports with from outside the type, and with sidesteps your factory -- Dice.D20 with { Sides = 0 } would sail straight past Of().  with waits for a later lesson by design, so students will walk past this on their own.  If a sharp student finds it, that is a real discovery:  they have found the one door the factory leaves open, and reconciling those two is exactly why with gets its own lesson later, alongside DTOs.  Leave it be -- a hole a student can see is the only kind worth teaching.
  • If they finish early: GameData/Items/Item.cs in the finished game validates by NORMALIZING -- negative weight becomes zero, an empty name becomes "Unknown Item", every value coerces, and construction stays wide open at all.  That is the opposite call from the one they just made.  Ask which is right.  (Both are.  It depends on whether a wrong item should stop the game.  It should let the player keep going -- a player with a weird item keeps playing.  A wrong die probably should, because every number after it is nonsense.)

Rubric reference (no points)

Standard
Make a type impossible to construct in an invalid state, using a private constructor and composing factory methods, and choose correctly between throwing and the Try pattern.
Getting StartedGuards still to write, or the build is red.  Next step: look at how the count guard inside Of() is written -- check the value, throw with a message naming the parameter, then get out.  Copy that shape for sides.  If you are getting CS9135, you tried to use MaxSides in a pattern; a pattern requires a const and this is a property, so write it as sides < MinSides || sides > MaxSides instead.
Got It WorkingOf() guards all three values, TryParse loads the seven valid lines and refuses the rest, and Scene 1's museum has been cleared of everything embarrassing.
Made It Mine ⭐…and my own Card has a private constructor with every rule behind a factory, a working TryParse, and a deck factory that prints 52 -- and I can say which of my rules catch bugs and which catch bad data.
Went Beyond…and I went after something the lesson left open -- an enum-based rank that makes "11H" impossible to express, a Result type in place of exceptions, a factory that composes so cleanly a new archetype is one line, or a real argument about where "2 d 6" belongs that I can defend from both sides.

⭐ Made It Mine is the goal for everyone. “Went Beyond” keeps its list open -- the examples are only starting points. Going somewhere the lesson left open is the whole idea.
